ТЕХНИЧЕСКОЕ РЕВЬЮ ВЕБ-СЕРВИСА

Архив: tweak-review.zip

Формат: независимое ревью исходников.
Проверялось: архитектура client/server, файловая структура, запуск/deploy, логика, мёртвый код, безопасность, реальные функции и заглушки.

==================================================
КРИТИЧЕСКОЕ / HIGH
==================================================

HIGH-01 — Публичный /api/route позволяет расходовать чужой OpenRouter-бюджет

Файл: api/route.js:139–177, 179–234

Проблема:
Endpoint принимает запросы без аутентификации, пользовательской сессии или rate limit.

Клиент сам управляет:
- системным промптом;
- пользовательским промптом;
- параметром параллельной генерации.

При parallel=true один HTTP-запрос запускает три отдельных вызова OpenRouter через Promise.all.

Как эксплуатируется:
Атакующий может не пользоваться интерфейсом, а напрямую отправлять POST /api/route с произвольным промптом и parallel=true, повторяя запросы автоматически.

Ключ OpenRouter находится на сервере, поэтому расходы идут через ключ владельца.

Лимит длины промпта не решает проблему: 20 000 + 60 000 символов на запрос всё равно позволяют выполнять множество платных запросов.

Как чинить:
- ограничить доступ к endpoint;
- ввести rate limit на IP/сессию/пользователя;
- сервер должен сам определять допустимые операции;
- не позволять клиенту произвольно задавать системный prompt;
- отдельно ограничить число AI-вызовов на единицу времени;
- иметь серверный лимит расходов/квоты.

--------------------------------------------------

HIGH-02 — Граница доверия к системному промпту отсутствует

Файл: api/route.js:167–168

Сервер получает от браузера:
- системный промпт;
- пользовательский промпт.

После этого отправляет их в OpenRouter как:
messages: [
  { role: 'system', content: системныйПромпт },
  { role: 'user', content: пользовательскийПромпт }
]

То есть «системный промпт» фактически не является доверенной серверной инструкцией.

Как эксплуатируется:
Любой клиент может заменить системный prompt на произвольную инструкцию или использовать endpoint для совершенно другой задачи.

Это не классическая prompt injection через пользовательский текст. Проблема архитектурная: сервер доверяет клиенту роль system.

Как чинить:
Системные инструкции должны находиться на сервере. Клиент должен передавать только структурированные пользовательские данные, а сервер сам формирует доверенный system prompt.

--------------------------------------------------

HIGH-03 — /api/weather имеет сильное увеличение количества внешних запросов

Файл: api/weather.js:229–265

Сервер принимает максимум 24 этапа.

Каждый уникальный этап может породить:
- 1 запрос к геокодеру;
- 5 запросов к архиву Open-Meteo — по одному за каждый из пяти лет.

Теоретический максимум для одного HTTP-запроса:
24 × 1 геокодирование + 24 × 5 архивных запросов = 144 внешних HTTP-запроса.

При этом endpoint также не имеет аутентификации или rate limit.

Как эксплуатируется:
Можно отправлять множество запросов с уникальными названиями городов и датами, заставляя сервер делать большое количество внешних запросов.

Кэш снижает нагрузку только при повторении тех же данных и только внутри конкретного экземпляра процесса.

Как чинить:
- rate limit;
- ограничить количество уникальных городов/этапов на запрос;
- ограничить число внешних запросов;
- не позволять анонимному клиенту бесконтрольно инициировать каскад внешних запросов.

--------------------------------------------------

HIGH-04 — Результат модели принимается как доверенные данные

Файлы: api/route.js:105–120, index.html:1878–1890

Сервер проверяет в основном только то, что модель вернула JSON.

На клиенте проверка также поверхностная: Array.isArray(результат.варианты) и наличие этапов.

Не проверяются строго:
- типы всех полей;
- количество этапов;
- количество отелей;
- числовые значения цен;
- отрицательные цены;
- даты;
- продолжительность;
- соответствие общей стоимости сумме составляющих;
- соответствие общей цены и цены на одного человека;
- визовые ограничения;
- уникальность стран;
- корректность перелётов.

Последствие:
Модель может вернуть структурно допустимый, но фактически бессмысленный JSON. Приложение продолжит обрабатывать его как достоверный результат.

Как чинить:
Ввести строгую серверную схему результата и проверять её до передачи клиенту. Не доверять модели ни структуру, ни числовые инварианты, ни фактические утверждения.

MED-01 — Реальные цены перелётов и отелей не получаются из внешних источников

Файл: index.html:2884–2900, api/route.js

В реальном режиме OpenRouter получает инструкцию самостоятельно сформировать:
- цены перелётов;
- цены отелей;
- названия отелей;
- детали рейсов;
- характеристики размещения.

В архиве нет API поиска авиабилетов, отелей или бронирования.

Следовательно, перелёты и отели не являются результатом обращения к соответствующим реальным источникам. Это результат генерации модели.

--------------------------------------------------

MED-02 — Демо-режим содержит полностью синтетические цены и погоду

Файл: index.html:2433–2730

Демо-режим действительно существует и работает локально.

Но его данные искусственные.

Перелёты:
построитьПерелёт() использует фиксированную базовую цену 25000 и вычисляет детали на основании длины строк городов.

Отели:
построитьОтели() использует фиксированные:
- 4000 ₽;
- 8000 ₽;
- 16000 ₽ за ночь.

Погода:
построитьПогоду() вычисляет температуру и осадки математически из длины названия города.

При этом текст результата утверждает:
«Согласно архиву погоды за последние 5 лет...»

хотя в демо это не архив, а синтетически рассчитанное значение.

Приложение помечает результат как ДЕМО-данные, поэтому факт подмены не скрыт полностью. Но сами значения внутри демо являются заглушками.

--------------------------------------------------

MED-03 — Ошибка AI автоматически превращается в демо-результат

Файл: index.html:2974–2993

Если реальный AI:
- не отвечает;
- возвращает ошибку;
- возвращает некорректный результат,

приложение вызывает сгенерироватьДемоВарианты() и продолжает работу.

Это означает, что пользователь может получить полноценный экран результатов даже после фактического сбоя AI.

Баннер сообщает о демо-режиме, поэтому это не скрытая подмена, но с технической точки зрения ошибка основного сервиса приводит к синтетическому результату.

MED-04 — Ограничение бюджета не гарантируется

Файл: index.html:2947–2955

Код сначала пытается удалить варианты дороже бюджета:

const вБюджете = результат.варианты.filter(...)

Но если все варианты дороже бюджета, они не удаляются:

if (вБюджете.length > 0) {
    результат.варианты = вБюджете;
}

То есть при отсутствии хотя бы одного подходящего варианта приложение оставляет варианты, нарушающие установленное ограничение бюджета.

Это противоречит собственным инструкциям модели в index.html:2873–2875, 2896.

--------------------------------------------------

MED-05 — Фильтр «без дождей» допускает «редкие дожди»

Файл: index.html:2001–2005, 2027–2047

Функция этапДождливый() считает дождливым только:
- «возможны дожди»;
- «часто...»;
- «идут дожди».

Но «редкие дожди» дождливым не считается.

При запросе «без дождей» вариант с «редкими дождями» может пройти фильтр.

--------------------------------------------------

MED-06 — Проверка ISO-даты принимает некоторые несуществующие календарные даты

Файл: api/weather.js:21–27

Проверка:
- /^\d{4}-\d{2}-\d{2}$/;
- Date.parse().

Этого недостаточно для проверки существования календарной даты.

Например, в используемом Node дата 2026-02-31 парсится и нормализуется в 2026-03-03.

Следовательно, API может принять календарно несуществующую дату и затем запросить данные уже для другой даты.

--------------------------------------------------

MED-07 — Serverless /api/route не имеет явного ограничения общего размера входного JSON

Файл: api/route.js:155–177

Ограничения применяются к двум строкам:
- системному промпту;
- пользовательскому промпту.

Нет явного ограничения общего размера req.body или строгой схемы объекта до его обработки.

На локальном сервере есть отдельный лимит 150 KB, но это другая реализация и он не применяется к Vercel serverless-функции.

НИЗКОЕ

LOW-01 — Декларируемая версия Node шире фактически используемого запуска

Файл: package.json:7, 14–16

Проект заявляет:
node >=18

Но запускается через:
node --env-file=.env.local dev-server.mjs

--env-file относится к более новым версиям Node и не является универсально доступной возможностью всего диапазона >=18.

Следовательно, декларация >=18 шире фактически поддерживаемой среды запуска.

--------------------------------------------------

LOW-02 — Локальный dev-server позволяет отдавать исходники проекта

Файл: dev-server.mjs:125–140

Проверка статических файлов блокирует:
- .env;
- .env.local;
- config.js;
- .git;
- node_modules;
- .vercel;
- package-lock.json.

Но api/route.js, api/weather.js, dev-server.mjs и другие исходные файлы не заблокированы.

При проверке:
GET /api/route.js → HTTP 200

Сервер отдаёт полный исходный код.

Это относится именно к самописному npm start dev-server. Это не означает, что Vercel production автоматически отдаёт эти файлы как статические.

--------------------------------------------------

LOW-03 — Локальный body limit не прекращает чтение входящего потока

Файл: dev-server.mjs:74–85

После достижения лимита тела 150000 байт Promise отклоняется, но обработчики data остаются подключёнными и продолжают получать поступающие куски.

Для локального dev-сервера это может использоваться для дополнительного расходования памяти при очень большом HTTP body.

==================================================
ГЛАВНЫЙ ТЕХНИЧЕСКИЙ ВЫВОД
==================================================

Самая серьёзная проблема архитектуры — публичный серверный AI-прокси без контроля доступа и с клиентским управлением system prompt.

Если проект задеплоен публично на Vercel с рабочим OPENROUTER_API_KEY, любой человек, знающий URL, потенциально может использовать сервер как бесплатный для себя прокси к платному OpenRouter-аккаунту владельца.

Параллельный режим дополнительно увеличивает расход до трёх AI-вызовов на один HTTP-запрос.

Вторая по значимости проблема — модель фактически является источником travel-фактов, которые интерфейс представляет как данные маршрута, при отсутствии интеграций с источниками перелётов/отелей.

Ревью намеренно ограничено техническими находками. Предложения по развитию продукта, новые функции и предположения о первоначальном замысле не включались.
